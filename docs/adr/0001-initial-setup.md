# ADR 0001: Початкова архітектурна структура

## Статус
Прийнято — 2026-09-23

## Контекст
Будуємо REST API для управління задачами на Python/FastAPI/PostgreSQL у Docker. Потрібна структура, яка забезпечить тестованість бізнес-логіки незалежно від фреймворків і БД, та дозволить безпечно розширювати проєкт.

## Рішення
Застосувати **Clean Architecture** з чотирма шарами — `domain`, `application`, `infrastructure`, `presentation` — та строгим dependency rule: залежності йдуть лише всередину, до `domain`.

Інструментарій:
- **FastAPI** — presentation, за швидкість, автогенерацію OpenAPI та нативну асинхронність.
- **SQLAlchemy 2.0 (async) + Alembic** — infrastructure, як стандарт де-факто для Python + PostgreSQL з підтримкою міграцій.
- **uv** — керування залежностями, швидший за pip/poetry.
- **pytest** — тести, дозволяє легко ізолювати `domain`/`application` без БД через фейкові реалізації портів.
- **ruff** — лінт і форматування в одному інструменті.
- **pyright** — статична типізація (strict), обраний замість mypy за швидкість і якість інференсу типів.

## Альтернативи, що розглядались
- **Layered/N-tier без інверсії залежностей** — відхилено: бізнес-логіка стає залежною від ORM, важче тестувати.
- **Hexagonal (Ports & Adapters) з портами всередині infrastructure** — по суті еквівалент, але порти свідомо розміщені в `application`, щоб чіткіше показати, що саме use cases визначають контракт, а не інфраструктура.
- **mypy замість pyright** — відхилено на користь швидкості перевірки та кращого editor-experience.

## Наслідки
- Кожна нова функціональність вимагає explicit use case в `application` та порт, якщо потрібен доступ до зовнішніх ресурсів.
- Домен залишається вільним від залежностей — легко purely unit-тестувати.
- Додаткова верстка (порти/інтерфейси) на старті проєкту — свідомий trade-off заради довгострокової гнучкості.
